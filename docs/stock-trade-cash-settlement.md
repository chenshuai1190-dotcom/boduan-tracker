# 股票交易与现金结算

## 口径

- 新账户固定定义为 `auth.users.created_at >= 2026-10-31T16:00:00Z`，即中国时区 2026-11-01 起注册，包括上线前已交易的账户；不是每月滚动改变旧用户模式。
- 买入现金变化为 `-(price × shares + fee)`；卖出为 `price × shares - fee`。现金不足或历史超卖时整个事务拒绝。仅支持可核对的 USD 现金账户；已有融资不能自动猜测借款或把现金变成负数。
- 初始资金属于现金基准。以模拟数据 200 万美元、200 股 × 500 美元、零手续费为例，剩余现金为 190 万美元；按成交价估值时现金加持仓仍为 200 万美元。
- 股票买卖是内部资产转换，不调用外部转入/转出 RPC，不增加外部资金流。手续费确实扣现金；现有报表自身的手续费口径不在本次暗改。
- `stock_trades.record_kind` 显式区分真实交易与历史汇总持仓。历史持仓不再次扣现金；备注修改不能偷偷改变已明确的金融类型。旧备注标记仅在明确核对旧账时兼容识别。
- 用户已取消独立历史持仓录入入口：新建默认真实交易，普通股票和 TQQQ 均不提供类型切换。现有历史类型只作兼容处理，移除入口不批量转为真实买单、不重复扣款，也不删改既有持仓。

## 已有账户与修复

- 老账户不批量修改现金，原手动余额语义保留。启用时必须确认当前现金已包含已有交易，已有交易标记为基准排除项。
- 本月已有交易的账户先预览开户资金修复。开户来源、现金版本、正式账本及资金流水必须可核对；后续手工校准、来源缺失或历史交易冲突时停止自动补扣。
- `preview_repair` 只读生成金额、交易数、基准日期及版本 token；`repair` 复核同一 token 后一次性补记并启用。无已发生交易的新现金账户首次正式买卖自动启用。
- 生产修复必须精确匹配授权账号，保留操作 ID、前后聚合证据，不依据昵称、截图或客户端计算直接覆盖数据库余额。
- 日期账本、持仓和现金必须采用相同收盘截止口径；回溯交易改删不能只调整当前余额。被手工校准覆盖的历史改动需要额外核对，不能默默忽略现金差额。

## 事务与权限

- 唯一客户端入口：`stock_trade_cash(p_action,p_payload,p_expected_user_id)`。服务端核验 JWT owner 与 expected user；内部账户、结算项、操作表均拒绝直接访问。
- 同账户使用现有 `available_cash:` advisory lock，先锁现金状态，再锁交易与账本版本。交易与现金一同提交或回滚。
- 操作 ID 在未知结果重试时保持不变；不同请求不得复用 ID。编辑和删除必须提供原 `updated_at`，不能覆盖另一设备的新版本。
- 幂等命中返回当前权威现金和交易状态，不能把第一次请求的旧余额覆盖回页面。
- 客户端收到同一已提交结果后同时刷新持仓和现金；账户切换或 ABA 会话边界拒绝交付旧结果。没有“RPC 失败后回退直写”的路径。
- 原启动时自动修正 `stock_trades.symbol` 的直接 UPDATE 停用；读取仍统一标准代码，显式正式修改走同一事务入口。

## 收盘与时间线

- 原始现金事件保留；结算追加可审计事件，历史已完成日补充一致的收盘现金，再标记个人报表 dirty。不得伪造交易时间或直接写入收益结果。
- 新现金事件及快照包含结算基准 ID 和累计交易现金 delta；快照字段由数据库从权威 cash event 填充。
- 时间线仅在同一基准且现金差额与内部交易 delta 完全一致时延续净资产比较；外部资金流、校准、来源缺失仍中断。其他收益、比赛与快照发布门禁继续沿用原链路。

## 发布与回查

1. FULL 检查包含实际 SQL 执行、双用户权限、原子失败、幂等、修改删除、手续费、超卖、余额不足及历史收盘边界。
2. 只读 preflight 核对表/函数版本、旧权限、目标账户开户事件及完整账本，保存业务聚合指纹。
3. 执行 `supabase/stock_trade_cash_foundation_20261109.sql`；此阶段不回写用户账户、不开放新写入口。确认新字段和函数的结构与权限。
4. 发布支持 RPC 的 runtime，然后执行 `stock_trade_cash_contract_after_runtime_20261109.sql` 原子切换。旧直写客户端提示刷新，不能绕开结算；切换期间新 runtime 不回退直写。
5. 按授权目标逐个预览/确认可证明的开户资金修复；不符合条件的账户保持待核对，不盲目全量扣款。
6. Postflight 核对现金等式、交易内容未改、结算操作唯一、快照 dirty 状态与其他账户未变，再执行一次匿名 REST 隔离检查。
7. 出现异常先停修复，保留原事件与审计；使用经过核对的前向修复。启用自动结算后不得直接恢复旧写权限或盲目回滚 runtime。
